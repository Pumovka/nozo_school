# Архитектура проекта

## Стек

- Next.js и React — приложение и интерфейс.
- TypeScript — типизация.
- Tailwind CSS и SCSS — стили.
- Feature-Sliced Design (FSD) — принцип организации кода.
- ESLint — статический анализ.
- Prettier — форматирование.
- Husky и lint-staged — локальные проверки изменённых файлов перед коммитом.

## Общие принципы

- Одна задача — одна отдельная ветка и pull request.
- Компоненты должны решать одну понятную задачу.
- Повторно используемые элементы выносятся в общие компоненты.
- Типы данных не дублируются без необходимости.
- Не отключайте правила ESLint ради прохождения проверки. Исправляйте причину ошибки или обсуждайте обоснованное исключение отдельно.
- Для MVP используйте моковые данные и клиентское состояние. Не добавляйте backend-интеграции без изменения согласованного объёма проекта.

## Слои FSD

Предполагаемое разделение кода:

- `app/` — маршруты Next.js, глобальные стили и провайдеры.
- `pages/` — композиция страниц, если она нужна при выбранной схеме маршрутизации.
- `widgets/` — крупные блоки интерфейса, например шапка или карточный список.
- `features/` — пользовательские действия, например поиск курса или изменение настроек доступности.
- `entities/` — предметные сущности: курс, урок, пользователь, прогресс.
- `shared/` — UI-компоненты общего назначения, утилиты и конфигурация.

Не нужно создавать пустые слои только ради соответствия схеме. Используйте слой, когда в нём действительно есть код.

## Направление зависимостей

- Верхние слои могут использовать нижние.
- Нижние слои не должны импортировать верхние.
- Общие компоненты не должны зависеть от конкретных страниц.
- Избегайте циклических импортов.
- Для импорта из `src/` настроен алиас `@/*`, например `@/shared/ui/button`, если такой путь соответствует реальной структуре проекта.

## Данные MVP

Пока backend не входит в проект, курсы, уроки, пользователи и прогресс могут храниться в моковых данных. Для сохранения пользовательского прогресса допускается `localStorage`.

Не храните в `localStorage` пароли, секреты или реальные чувствительные данные. Данные в браузере не являются защищённым хранилищем.

## Доступность

Доступность учитывается при проектировании компонентов, а не только на отдельной странице. Проверяйте семантическую HTML-разметку, управление клавиатурой, видимый фокус, подписи элементов формы, контраст и понятные сообщения об ошибках.

Цель — следовать применимым рекомендациям WCAG 2.2 AA. Не заявляйте о полном соответствии стандарту, пока оно не проверено.
